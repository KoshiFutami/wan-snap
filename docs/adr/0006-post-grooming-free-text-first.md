# 0006. トリミング情報を Post に紐づける（フリーテキスト先行）

- **ステータス:** Accepted
- **日付:** 2026-05-19

## 背景

ユーザーはトリミング後のコーデを投稿することが多く、「このコはどこでカットしてもらったか」という情報を投稿に付加したいというニーズがある。
また、将来的には「トリミング投稿だけを絞り込む」「サロンごとの施術例を見る」といった体験も実現したい。

一方で、初期からサロンのマスタデータを設計するとユーザーがサロンを登録・選択するUXの設計が必要になり実装コストが高い。

## 判断

`PostGrooming` テーブルを Post に 1:0..1 で追加し、サロン名はフリーテキストで保持する。
サロンのマスタ化（`GroomingSalon` モデル）は将来フェーズで行う。

## 理由

**フリーテキスト先行を選んだ理由:**

- 「トリミング後バッジ」と「トリミング投稿絞り込み」は `post_groomings` の有無で判定できるため、マスタなしで実現可能
- サロンマスタを最初から作ると「どこでサロンを登録するか」「表記ゆれをどう吸収するか」という UX 問題が先行し、本来の価値提供が遅れる
- `salonName`（フリーテキスト）と `salonInstagram` を持っておくことで、後からマスタへの正規化が可能

**検討した代替案:**

- *PostItem の category を "GROOMING" に拡張する:* 商品とサービスを同じ型で扱うため概念が合わない。`purchaseUrl` や `priceJpy` がトリミングには意味をなさず、フィールドが腐る
- *最初から GroomingSalon マスタを作る:* 将来的には必要だが、フリーテキストから始めて後で正規化するほうがリスクが低い

## 結果

- `post.grooming != null` でトリミング投稿かどうかを判定できる
- `WHERE grooming IS NOT NULL` でトリミング投稿の絞り込みが可能（フィルター機能追加時）
- サロン名の表記ゆれは許容する（正規化は将来フェーズ）
- 将来フェーズで `GroomingSalon` マスタを追加し、`post_groomings.salon_id` を追加して既存データを正規化する
- `grooming` と `items` は排他にしない。「トリミング後にアクセサリーも着けている」投稿は自然にあり得るため共存を許容する
- UI 側でのみ制御する：トリミング情報が入力されている場合、アイテム登録セクションに「アクセサリーも付けていたら追加してね」等のガイドテキストを表示してノイズを防ぐ
