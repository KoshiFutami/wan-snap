# 0001. posts/dogs モジュールに DDD を採用

- **ステータス:** Accepted
- **日付:** 2026-05-14

## 背景

Wan Snap は「犬のコーデスナップ × アイテム構造化データ」を核とするサービスで、
投稿（Post）と犬プロフィール（Dog）がビジネスロジックの中心になる。
一方、auth・users・likes はセッション管理やカウント操作であり、複雑なビジネスルールを持たない。

すべてのモジュールを同じアーキテクチャで実装するかどうかを判断する必要があった。

## 判断

posts・dogs モジュールは DDD（Domain / Application / Infrastructure / Presentation の4層）で実装する。
auth・users・likes はシンプルな CRUD アーキテクチャで実装する。

## 理由

**DDD を選んだ理由（posts/dogs）:**

- ドメインルールが複数ある（集約不変条件、所有者チェック、タグ重複排除など）
- 将来的な拡張（タグ enum 化、いいね数キャッシュ、画像複数枚対応）で変更が集中するため、ドメイン層を隔離しておく価値がある
- `fitNote`（サイズ感メモ）や `PostItem` の構造化など、サービスの差別化要素がドメインモデルに直結している

**CRUD を選んだ理由（auth/users/likes）:**

- ビジネスルールが薄い（JWT 発行・ユーザー情報の保存・いいねのフラグ管理）
- DDD を適用するとレイヤーだけが増えて実態のないコードになる
- 開発スピードとコードの読みやすさを優先

**検討した代替案:**

- *全モジュールを CRUD:* シンプルだが、Post の集約不変条件や将来の拡張に対応しにくい
- *全モジュールを DDD:* 一貫性はあるが、auth/likes に DDD は過剰設計

## 結果

- posts/dogs の変更コストが上がるが、ドメインルールの変更に強くなる
- auth/users/likes は薄くシンプルに保てる
- 新しい開発者が参加した際、「どのモジュールがどのアーキテクチャか」を AGENTS.md で把握できるようにする必要がある
